# F28 — GPG signing and verification — 2026-09-22

F28 now supports explicit GPG signing for commits, amended commits and annotated tags, an
Unsigned override, and Git-default behavior. The repository signing-key editor shows effective
and repository-local values, Git's format and commit/tag defaults, and offers removal of the local
override. It writes only `user.signingkey`; global settings, key generation/import and trust management
remain in Git/GPG. Local configuration is shared by linked worktrees; higher-priority worktree and
environment values can still override it.

Commit details (including the separate inspector) and Tag Details offer explicit verification.
The backend verifies exact object IDs and distinguishes valid trusted, valid untrusted, invalid,
missing public key, expired, revoked, unsigned, unsupported and unavailable results. It does not
equate unsigned or failed verification with a trusted signature. Verification is refreshed on demand,
so changes to the installed keyring are not hidden behind a persistent signature cache.

## Boundaries and validation

Three named capabilities extend shared schemas, preload and authorized handlers together:
`getSigningSettings`, `setSigningKey`, and `verifySignature`. Commit/reference requests gain a bounded
signing enum without changing their channels. Configuration writes revalidate a settings snapshot and
share the common-directory mutation queue. Git's single-key config write preserves unrelated entries.
Inspectors can verify, but cannot configure signing. No arbitrary command, private key or passphrase
field crosses IPC. GPG uses its installed agent/pinentry; signer diagnostics are suppressed in signed
commit results and tag creation results. Verification exposes status and a public fingerprint only.

Signed writes retain the existing operation lifecycle, timeout and process-group cancellation. A
cancelled operation is never automatically retried, and cancellation does not promise rollback after
Git has already updated a reference. Verification has a 10-second/1-MiB bound and runs only on request.
Other configured signing backends can still be used by Git-default operations, but their verification
is explicitly unsupported here; no SSH/X.509 parity claim is made.

`tests/unit/signing-service.test.ts` uses disposable repositories, isolated global configuration and a
new isolated GPG keyring. It checks signed commit/amend/tag objects against Git, invalid content,
unavailable keys, unsigned override, cancellation with preserved HEAD/index, config inheritance and
linked-worktree scope, stale configuration and trust-status classification. Preload and inspector tests
check malformed DTOs and read/write authorization. The Electron scenario exercises key Save/Cancel,
signed commit, verified details, signed tag, nested-dialog Escape and invalid request rejection.

Native graphical pinentry with a passphrase-protected key, smartcards, platform-specific agent setup,
key import/trust editing, global settings pages and SSH/X.509 verification remain unverified or outside
this bounded workflow. Expired/revoked states have parser coverage, not a live expiring/revoked key trial.
P10 remains partial: these results do not complete rich images, authenticated LFS or locks.
